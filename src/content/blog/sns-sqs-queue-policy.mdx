[検証リポジトリ](https://github.com/rikukaInoue/greenfield)のイベント連携は
outbox パターンで作ってある。業務データと同一トランザクションで outbox テーブルに
イベントを書き、relay が SNS FIFO トピックへ publish、購読する SQS FIFO キューから
consumer が受けて inbox テーブルで重複を弾く。開発は LocalStack で回してきた。

これを**バスだけ実 AWS**（アプリと DB は手元のまま）に差して、同じ検査スクリプトを
流した。結論から言うと、アプリのコード変更は 0 行で済んだ一方、
**LocalStack では検査されていなかったものが1つ**見つかった。

## 差し替えに必要だった変更: アプリ 0 行

relay / consumer は AWS SDK の `LoadDefaultConfig` を使っているので、
`AWS_ENDPOINT_URL` を消して実物のトピック ARN とキュー URL を環境変数で渡すだけで
実 AWS に向く。変更が要ったのは開発用ツール側だけで、

- トピック・キューを作る管理コマンドが、LocalStack 用のエンドポイント上書きと
  **ダミーの静的資格情報を常に注入していた**（実 AWS では共有資格情報ファイルより
  優先されて `InvalidClientTokenId` になる）
- 検査スクリプトが LocalStack 用の環境変数を強制していた

どちらも「`aws` という値を渡したら SDK の既定解決に任せる」分岐を足して解決した。

## Publish は成功し、配送だけが消えた

初回実行の結果が興味深かった。outbox → relay → SNS publish までは全部成功する。
outbox の `published_at` も付く。しかし **consumer には何も届かない**。

原因は SQS の**キューポリシー**の欠如だった。SQS キューは既定では所有者しか
操作できず、SNS がキューへ SendMessage するには明示の許可が要る:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "sns.amazonaws.com" },
    "Action": "sqs:SendMessage",
    "Resource": "<キューの ARN>",
    "Condition": { "ArnEquals": { "aws:SourceArn": "<トピックの ARN>" } }
  }]
}
```

これが無いときの挙動が問題で、

- **Publish はエラーなく成功する**（送信側からは正常に見える）
- 配送だけが捨てられる。DLQ を設定していなければ**痕跡が一切残らない**
- そして **LocalStack はキューポリシーを強制しない**ので、ポリシー無しでも全部届く

つまりローカルの検査がいくら通っていても、実 AWS の認可は一度も検査されていなかった。
「送れた」は「届く」を含意しない。届いたことは受信側でしか確認できず、その確認を
認可を強制しない代替環境でやっても、認可の穴は見えない。
[fail open](/blog/checks-fail-open/) の典型がまた1つ増えた形になる
（検査は正しく、検査の走る環境に検出対象が存在できないパターン）。

対策はツール側でポリシーを必ず設定するようにした。LocalStack でも無害なので、
環境で分岐せず常に付ける。

## デデュープ窓の実測差: 配送は同じ、MessageId が違う

FIFO トピックには5分のデデュープ窓がある。同一 `MessageDeduplicationId` で
本文だけ変えて2回 publish して比べた:

| | 実 AWS | LocalStack |
|---|---|---|
| 2回目の Publish | 成功（エラーなし） | 成功（エラーなし） |
| 配送 | 1通のみ | 1通のみ（同じ） |
| MessageId | **2回とも同一** | 2回とも別 |

配送が1通に抑えられる挙動自体は LocalStack も再現する。違うのは MessageId で、
実 AWS は2回目にも**1回目と同じ MessageId を返す**。これは送信側が重複を検知できる
唯一の信号だが、LocalStack では毎回別の ID が返るので、この信号に依存するコードは
ローカルで検証できない。

この構成では relay が `MessageDeduplicationId = イベントID` を明示しているので、
再送が5分窓に入ればバスが吸収し、窓の外に出ても inbox が弾く。二段の防御が
実バスで両方確認できた。

## 順序と全体の検査

同一 `MessageGroupId` へ5イベント連投して、受信順は 1→5 の完全順序だった。
グループ ID を集約 ID にする設計（同一集約内は順序保証、集約間は並行）が
実バスでそのまま成り立つ。

キューポリシーを直した後は、検査スクリプト全体（outbox 残留 → relay 起動で送信 →
inbox 記録 → 重複スキップ → 再送で副作用1回）が実バスで全部通った。所要 14.8 秒で、
LocalStack とほぼ変わらない。使い終わったトピックとキューは当日中に削除し、
費用はリクエスト課金のみで $0.01 未満だった。

## まとめ

- LocalStack で開発した SNS/SQS 構成は、アプリ 0 行で実 AWS に差せた
- ただし **LocalStack が強制しないもの（キューポリシー）は、ローカルでいくら
  検査しても検査されていない**。実物での再演はこの1点だけでも価値があった
- 配送の失敗は送信側から見えない。届く側で確認するか、DLQ を置くか、
  少なくとも一度は実物で通すこと
