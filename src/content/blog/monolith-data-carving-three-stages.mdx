## はじめに

モノリスからサービスを切り出す話は、コードの分け方（モジュール境界、
ストラングラー・フィグ）として語られることが多い。しかし実際に手が止まるのは
データです。テーブルは JOIN と外部キーで絡み合っていて、しかも書き込みは
移行の間も止まらない。

この記事は、データの切り出しを**3段階**に分ける整理です。段階を分ける基準は
1つだけ:

> **1つのトランザクションが、新旧両方の置き場所に届くか。**

これが届く間は普通の道具で進められる。届かなくなった瞬間に、必要な装備が
一段重くなる。だから「どこまで届く状態を保ったまま、何を済ませておくか」が
移行設計のほぼすべてになります。

## 段階1: 同じ DB・同じスキーマのまま、コードだけ分ける

いわゆるモジュラーモノリス。コードの所有権（このテーブルに触ってよいのは
このモジュールだけ）を決めて守らせる段階で、データは何も動かしません。
JOIN も外部キーもトランザクションも全部そのまま使える。

この段階の仕事は**現状を測ること**です。どのテーブル間に外部キーが張られて
いるかを棚卸しすると、「このモジュールを独立させるには、あと何本の結合を
切る必要があるか」が数字になる。禁止でなく計測として回すのがポイントで、
ベースラインを固定して**増加だけを CI で止める**と、移行の逆行を防ぎながら
削減を進捗として見られます（[fk:check の警告モードとして実装した話](https://github.com/rikukaInoue/greenfield/issues/197)）。

## 段階2: 同じ DB インスタンスの中で、database を分ける

`orders` モジュールのテーブルを `orders` database へ、`inventory` の
テーブルを `inventory` database へ。物理サーバは1台のままです。

ここが**一番おいしい段階**です。理由は、切り出しの難所を「まだトランザクションが
張れる安全な場所」で済ませられるから:

- **跨ぎ JOIN と跨ぎ外部キーをここで捨てる**。他 database のテーブルを参照せず
  ID を値として持つ、存在確認は相手モジュールの API か複製ビューで、という形に
  書き換える。書き換え中に問題が出ても、同一インスタンスなので巻き戻しは安い
- **データの移送もここでやる**。テーブルを別 database へ動かす作業は、
  同一トランザクションで二重書きできるうちは[オンラインマイグレーションの
  標準装備](/blog/progressive-delivery-db-side/)（二重書き → バックフィル →
  読み切替 → 旧側を削除）がそのまま使える。カラム改名と同じ型で、対象が
  テーブルに変わるだけ

注意が1つ。この段階では跨ぎのトランザクションが**技術的にはまだ張れて
しまう**。MySQL は database を跨ぐ FK も JOIN もエラーにしないので、
「張れるけど張らない」を文章でなく CI（跨ぎ FK の検査）で守る必要が
あります。ここを規律で守れない場合、段階3に進んだ瞬間に「張れなくなって
初めて発覚する結合」が一斉に火を吹きます。

## 段階3: 別インスタンスに分ける

AWS で言えば **RDS インスタンス（Aurora ならクラスタ）をサービスごとに
別にする**段階です。紛らわしいのは Aurora のリーダー/ライター構成で、
同一クラスタ内のレプリカは書き込み1系統の同じトランザクションドメイン
なので段階3ではありません。「クラスタごと別」が段階3です。

| | AWS 上の形 | トランザクション | 障害・運用 |
|---|---|---|---|
| 段階2 | 1つの RDS インスタンスに複数 database | まだ張れる（規律で禁じる） | フェイルオーバー・メンテ・スケールが運命共同体 |
| 段階3 | サービスごとに別インスタンス/クラスタ | 物理的に張れない | 別々に落ち、別々にメンテでき、別々にスケールする |

段階3で装備が一段重くなる理由は、**二重書きが原子でなくなる**ことです。
段階2までは「旧テーブルと新テーブルへの書き込み」を同一トランザクションに
入れられた。インスタンスが分かれると「旧側は成功、新側は失敗」が構造的に
起こるので、二重書きそのものが信用できない。代わりに:

- 旧側の書き込みと**同一トランザクションで outbox テーブル**に変更を積み、
  relay が新側へ運ぶ（at-least-once + 受信側の重複排除。
  [実バスで検証した形](/blog/sns-sqs-queue-policy/)と同じ装備）
- あるいは定期の検算 + 修復で差分を潰す形にして、不整合の窓を許容する

つまり段階3のデータ切り出しは、オンラインマイグレーションの装備に
**イベント連携の装備（outbox / 重複排除 / 再送）を足したもの**になります。

ただし、段階2を経由していれば段階3の引っ越し自体は**データの意味を変えない
移送**に縮んでいます。MySQL なら binlog レプリケーション（`replicate-do-db` で
対象 database だけ）を新インスタンスへ張り、追いついたら DSN を切り替えるのが
定石。DMS でも可。切替のリハーサルには [Aurora fast clone
（データ量非依存で5分半）](/blog/aurora-instant-ddl-fast-clone/)がそのまま使えます。

## 段階2で止まるのは撤退ではない

段階3に進むと、インスタンス台数分の固定費（db.t4g.medium でも1台 $80/月前後）と、
跨ぎトランザクション不能に伴うイベント連携装備の常設が付いてきます。
これに見合う要求は「別々に落ちてほしい」「別々にスケールしたい」
「チームごとに運用を分けたい」のどれかが現実になったときで、
それまでは**段階2 + 跨ぎ FK の CI 検査**で止まるのが合理的です。

大事なのは、段階2で止まっていても**段階3への切符を持ち続けている**こと。
跨ぎ FK ゼロ・跨ぎ JOIN ゼロ・跨ぎトランザクションゼロが CI で守られている限り、
段階3は「いつでも実行できる引っ越し」であって「いつか来る手術」ではない。
逆に規律が破れていると、切符は静かに失効します — 破れたことは
段階3を試みるまで誰にも見えないので。

## まとめ

- 境目は「1つのトランザクションが新旧両方に届くか」。届く間（段階1〜2）に
  難所（FK 切り・JOIN 排除・データ移送）を済ませるのが移行設計の本体
- 段階1の道具は**棚卸しと逆行防止**（FK のペア別集計 + ベースライン差分）
- 段階2の道具は**オンラインマイグレーションの標準装備**（二重書き →
  バックフィル → 読み切替 → 削除）。まだ原子的にできるうちに使う
- 段階3の道具は**outbox 以下のイベント連携装備**。二重書きが原子でなくなる
  ことへの答えで、引っ越し自体は段階2を経ていれば意味を変えない移送に縮む
- 段階2で止まるのは合理的。ただし切符（跨ぎゼロの CI 検査）は握り続ける
