## はじめに

新しいバージョンを本番に出す、という一つの行為に見えるものは、実際には3つの別々の営みでできています。

1. **置く**（デプロイ）: 新しいバイナリを本番環境に配置する
2. **当てる**（トラフィック制御）: 実ユーザーのリクエストをどの版に、どれだけ向けるか
3. **見せる**（リリース）: 機能をユーザーの目に触れさせるか

一括リリースとは、この3つを同時に、全量で、一発でやることです。うまくいけば速い。失敗すると全ユーザーが同時に被弾し、戻す手段は「もう一度一括で置き直す」しかない。

**プログレッシブデリバリーは、この3つを分解して、それぞれを段階的・可逆的にする考え方**です。この記事はその全体地図と語彙を整理します。個々の数字は検証環境（Go + ECS + MySQL/Aurora）で実測したものです。

```mermaid
graph LR
    subgraph 置く
        D["デプロイ<br/>新版を配置(まだ誰も見ない)"]
    end
    subgraph 当てる
        G["昇格ゲート<br/>テストトラフィックで検証"] --> C["カナリア<br/>n% だけ当てる"] --> F2["全量切替"] --> BK["bake<br/>旧版を温存して監視"]
    end
    subgraph 見せる
        FL["フィーチャーフラグ<br/>機能の公開を独立に制御"]
    end
    D --> G
    BK --> FL
```

## 「当てる」の語彙

トラフィック制御の部品は4つ覚えれば足ります。

| 語彙 | 何か | 何を守るか |
|---|---|---|
| **Blue/Green** | 新旧2系統を並走させ、ロードバランサの向き先を一斉に掛け替える | 切替そのものの無停止（実測: 切替をまたぐ503リクエストで非200ゼロ） |
| **カナリア** | まず n% だけ新版に当てて観測し、問題なければ全量へ | 壊れた版の被害を「全量」から「n%」に縮める |
| **昇格ゲート** | 本番トラフィックを当てる**前**に、テスト用の経路で新版を検証する | テストで再現できる壊れ方の**被弾ゼロ** |
| **bake** | 全量切替の後も旧版を落とさず併走させる監視時間 | 即座に戻れる状態の温存（戻すのはLBの向き先変更だけ） |

大事なのは、これらが**代替関係ではなく直列**だということです。同じ「壊れた版」（ヘルスチェックは正常・書き込みだけ 500 を返す）を流して測った被弾数がそれを示します。

| 構成 | 被弾 |
|---|---|
| 昇格ゲートあり | **0 / 1,679**（ゲートが本番前に捕捉、103秒で自動ロールバック） |
| ゲートなし、カナリア20% + アラーム | **69 / 2,880（2.4%）**（検知窓の間に流れた分は失敗する） |

この対比が入門で一番伝えたい数字です。**カナリアは失敗を消しません。** カナリア中に新版へ流れたリクエストは、新版が壊れていれば失敗します。カナリアの価値は「全量事故を n% の事故に縮める」ことであり、失敗をゼロにするのはその手前の昇格ゲートの仕事です。

## 「見せる」の語彙: フィーチャーフラグ

デプロイと切り離して機能の公開を制御するのがフィーチャーフラグです。コードは本番に「置いて」あるが、フラグが無効なら「見せて」いない — この分離により、機能の公開・撤回がデプロイなしでできます。

実測では、フラグ反転がユーザーに届くまで **14秒・再起動なし**でした。デプロイの巻き戻し（後述の `stopDeployment`、32秒）と並ぶ、もう1本の巻き戻しレバーです。

ここでの誤解も正しておきます。「フラグの方が速いなら、事故対応は全部フラグでいいのでは」— なりません。**フラグで隠せるのは、コードが正しく動く前提での見せ方だけ**です。壊れたバイナリはフラグの後ろでも壊れ続けます（ログとリソースを汚しながら）。バイナリの問題はデプロイのレバーで、見せ方の問題はフラグのレバーで。2本を独立に保つから、どちらも迷わず引けます。

| 事象 | 引くレバー | 実測 |
|---|---|---|
| バイナリが壊れていた | デプロイの巻き戻し（`stopDeployment`） | 32秒で本番復帰 |
| 機能の見せ方を引っ込めたい | フラグ反転 | 14秒で全ユーザーへ |
| フラグ基盤自体が死んだ | 何もしない | コードに宣言した既定値で稼働継続 |

3行目も設計の一部です。フラグの既定値は「フラグ基盤が死んだときの安全側」を宣言する場所で、これを決めてあればフラグ基盤の障害がサービス停止に化けません。

## N-1 互換性 — DB は徐々に切り替えられない

ここまでの「当てる」の話はすべて、**N-1 互換性**という前提の上に立っています。新旧1世代差のバイナリが同時に正しく動けること — B/G もカナリアも bake も、**新旧のバイナリが同時に動く時間**を作るからです。トラフィックは 20% と 80% に割れますが、**データベースのスキーマは1つしかありません**。新旧両方のバイナリが、同じスキーマで正しく動く必要がある。

つまりアプリ層のプログレッシブデリバリーは、DB 層に「新旧互換なスキーマ変更」という別種の規律を要求します。トラフィックのように割合で割る話ではなく、**時間で分ける**話（互換を保って先に広げ、旧版が消えてから縮める）になる — この非対称性は1本の記事に値するので、[アプリと DB でプログレッシブは別物](/blog/progressive-delivery-app-vs-db/)として続編に分けました。

## まとめ

- プログレッシブデリバリー = 「置く・当てる・見せる」を分解し、それぞれを段階的・可逆的にすること
- 「当てる」の部品（ゲート → カナリア → bake）は直列であり、守るものが違う。**カナリアは失敗を消さない**（0/1,679 vs 69/2,880）
- 巻き戻しのレバーは2本（デプロイ32秒 / フラグ14秒）。速さでなく**管轄**で使い分ける
- すべての前提は N-1 互換性。トラフィックは割合で割れるが DB のスキーマは割れないので、ここから先は層ごとに別の話になる
