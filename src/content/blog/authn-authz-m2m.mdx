認証まわりの設計が崩れるときは、たいてい「ログインしているか」という if から
書き始めている。この1個の if に、実際には**3つの別の質問**が混ざっているからだ。

1. **誰か**（認証 / Authentication）
2. **この操作をしてよいか**（認可 / Authorization）
3. **何が見えるか**（認可付きの一覧）

検証用のリポジトリでこの3つを分けて組み、人間のログインと M2M
（サービス間のマシン認証）を同じ枠に載せるところまで実測した。その整理。
例は前の記事と同じ写真投稿サービス（写真の所有者・公開範囲・運営者がいる）。

## 認証: 「誰か」だけを確定させる

認証の出力は**主体（Principal）1個**に絞る。

```go
type Principal struct {
	Subject string   // OP が発行した識別子。解析しない・意味を持たせない
	Kind    Kind     // user | service
	Scopes  []string
}
```

検証は OIDC の標準に乗る: issuer のディスカバリから公開鍵（JWKS）を引き、
JWT の署名・有効期限・`iss` を検査して Principal に落とす。ここで重要なのは、
**認証はリソースのことを何も知らない**こと。「この写真を見てよいか」は
認証の仕事ではない。誰かが分かったら、それ以降の質問は全部認可に渡す。

そして M2M。サービス間の呼び出しでは、呼び出し元サービス自身が主体になる。
トークンの**取得の儀式**は人間と違う（人間は Authorization Code + PKCE で
ログイン画面を経由し、サービスは client_credentials で ID とシークレットを
直接交換する）が、**受け取る側の検証はまったく同じ JWT 検証1本**だ。
違いは Principal の `Kind` が `service` になることと、`Subject` の代わりに
クライアント ID が入ることだけ。受信側に「人間用の認証」「サービス用の認証」
という2系統を作らない。これが「M2M を同じ枠に載せる」の意味で、
検証経路が1本だと、後述の 401/403 の意味論も1つで済む。

## 認可の質問は2つある

認可には形の違う質問が2つあり、実装も分ける必要がある。

**質問1: この操作をしてよいか（Can）**

```go
Can(ctx, Request{Action: "photo.edit", ResourceType: "photo", ResourceID: "42"})
// → Allowed: true / false
```

**質問2: 何が見えるか（ListAccessible）**

一覧はこちらで、Can のループでは書けない。全件取ってから1件ずつ Can を聞くと
N+1 になるうえ、**先に件数を絞ってから認可で落とすと取りこぼす**（LIMIT 20 で
取った20件のうち5件しか見えなければ、画面には15件しか出ない）。

正しい形は「見える ID の集合を先にもらい、SQL の WHERE IN で絞る」。

```go
ids, _ := authz.ListAccessible(ctx, "photo.view", "photo") // 認可サービスに聞く
// SELECT ... FROM photos WHERE id IN (?) AND status = 'ready' ORDER BY ... LIMIT ?
// 公開範囲や件数の絞り込みは SQL 側でやる（Go 側で絞ると同じ取りこぼしが起きる）
```

一覧の直後に「作成した本人が自分の一覧を見る」ケースがあるので、
認可サービスの読み取りには一貫性ヒント（作成直後も見える強めの読み）を
透過させる。ここは実測して「作成直後可視」を確かめた。

## 権限は関係（Relation）で表す

「誰が何をできるか」を権限テーブルで持ち始めると、運営者・共有・組織と
増えるたびに列が増える。ReBAC（Relationship-Based Access Control）は
これを**主体とリソースの関係のグラフ**で表す。

このリポジトリの最小モデルは3型だけ。

```
user
platform
  operator: [user]          ← 運営者は platform への関係として1回だけ書く
photo
  parent: [platform]
  owner:  [user]
  viewer: owner または parent の operator   ← 直接割り当てない。導出する
  editor: owner または parent の operator
```

設計の要点は2つ。

- **viewer / editor は直接割り当てない。** owner という事実と、
  platform の operator という事実から**導出**する。「見せる」を配って回ると
  剥奪が漏れる。事実（所有・運営）だけを書き、権利は計算で出す
- **運営者の権限に専用機構を作らない。** 管理画面の「admin なら通す」if を
  書く代わりに、`photo の parent は platform` `platform の operator は運営者` の
  2本の関係で、運営者の閲覧・編集が普通の認可判定として導出される。
  権限の特例が if 文でなくモデルの中にあるので、監査で追える

もう1つ、語彙の境界がある。プロダクト側のコードが使うのは
`photo.view` のような **action の語彙だけ**で、それが viewer という relation に
対応することは認可サービスの中に閉じる。

```go
var mapping = map[string]string{
	"photo.view":       "viewer",
	"photo.edit":       "editor",
	"photo.publish":    "editor",   // 公開も編集権で判定する、という判断がここに残る
	"platform.operate": "operator",
}
```

relation の設計を変えても、プロダクトのコードは1行も変わらない。

## scope は権限ではなく「呼び出し文脈の枠」

混同しやすいのが scope の位置づけだ。scope はリソースへの権限ではない。
**このトークンでどの面（API 群）に入れるか**という、呼び出し文脈の枠である。

写真サービスには3つの面がある: 一般ユーザー向け、運営向け、サービス間。
サービス間の面には `internal:photo` という scope を要求する。すると:

| 呼び出し | 結果 | 理由 |
|---|---|---|
| トークンなしで内部 API | **401** | 誰か分からない（認証の失敗） |
| 人間のトークンで内部 API | **403** | 誰かは分かるが、このトークンは内部面の枠外（認可の失敗） |
| M2M でも scope なし | **403** | サービスであることと、枠を持つことは別 |
| M2M + `internal:photo` | 200 | 枠の中。この先でさらにリソース認可が走る |

401 と 403 を使い分けるのは呼び手のためだ。401 は「トークンを取り直せ」、
403 は「取り直しても無駄。権限の問題」を意味する。ここが混ざっていると、
クライアントは失敗時に何をリトライすべきか判断できない。

整理すると、認可判断は**二段**になっている。

```
scope 検査     … このトークンはこの面に入れるか（文脈の枠。粗い）
関係の判定     … この主体はこのリソースに何ができるか（細かい）
```

scope で関係の判定を代用しようとすると `photos:read:own` のような
擬似リソース権限が scope に増殖していく。逆に関係だけで面を守ろうとすると
「内部 API に人間のトークンで入れてしまう」穴が開く。両方要る。

## M2M の認可: サービスの権限と、ユーザーの代理

サービス間呼び出しでは、認可の主体に2つの候補がある。

- **サービス自身の権限で動く**: 定期バッチが全公開写真を集計する、など。
  主体は `service:collector` で、scope とサービス向けの関係で判定する
- **ユーザーの代理で動く**: 注文サービスがユーザーの写真情報を引く、など。
  この場合、**誰のための呼び出しかを引数として明示的に渡し**、受けた側が
  そのユーザーを主体として認可サービスに聞く

後者でやりがちな失敗は、scope `internal:photo` を持っているからと
リソース認可を省くことだ。scope は「注文サービスは写真の内部面を呼べる」
までしか言っていない。「そのユーザーがその写真を見えるか」は別の質問で、
省くと内部 API が権限昇格の抜け道になる。

M2M のトークン管理（取得・期限までのキャッシュ・自動付与）は
共通のクライアント基盤に置き、業務コードからは見えなくする。
人間の開発用トークンも同じ経路に流すと、開発と本番で通り道が変わらない。

## 全部 interface の後ろに置く

最後に配線の話。ここまでの部品は全部、プロダクトから見れば interface だ。

```go
type Authenticator interface{ Middleware() func(http.Handler) http.Handler }
type Authorizer    interface{ Can(ctx, Request) (Result, error) }
type Lister        interface{ ListAccessible(ctx, action, resourceType string) ([]string, error) }
```

開発中はローカル実装（署名検証なしの開発トークン + DB 1枚の擬似 ReBAC）で
動かし、本番アダプタ（OIDC 検証 + 認可サービス + OpenFGA）へは合成ルートの
差し替えだけで移る。検証リポジトリで実際に差し替えたときの
**usecase / handler の diff はゼロ**だった。認証・認可は横断的関心事の中でも
特に「あとから本物に差し替える」ことが確定している領域なので、
差し込み口を最初に切っておく価値が大きい。

## まとめ

| 質問 | 答える仕組み | 粒度 |
|---|---|---|
| 誰か | OIDC の JWT 検証（人間も M2M も同じ1本） | — |
| この面に入れるか | scope | 粗い（呼び出し文脈） |
| この操作をしてよいか | Can → 関係の導出 | 細かい（主体×リソース） |
| 何が見えるか | ListAccessible → WHERE IN | 細かい（集合） |

- 認証は Principal を作るだけ。リソースを知らない
- 権利は配らず、事実（所有・運営）から導出する。運営者も特別扱いしない
- scope は枠、関係は権利。**片方でもう片方を代用しない**
- M2M は取得の儀式が違うだけで、検証・認可の枠は人間と同じ。
  ユーザーの代理のときは、誰のためかを明示して細かい認可を省かない
