[前の記事](/blog/architecture-as-code/)で「『成功した』は『何も見ていない』と
区別がつかない」という節を書いた。そのあと2日間、検証リポジトリの作業で
**同じ形の穴を合計5回**踏んだ。形が完全に同じなので、カタログにしておく。

先に用語を1つ。**fail open** とは、制御や検査の機構そのものが壊れたときに、
結果が「許可・成功」として出てしまうことを指す（逆に、壊れたら「拒否・失敗」
として出るのが fail closed）。セキュリティの語彙だが、CI の検査・readiness・依存解決まで、
「何かを確かめる仕組み」全般に同じ力学が働く。

**検査のバグは、ほぼ必ず fail open になる。** 検査は「問題を見つけたら失敗」
という構造なので、検査自体が動かない・対象に届かない・対象が空、のどれでも
「問題は見つからなかった」＝成功として終わるからだ。

## 事例1: エラー出力を捨てたら、エラーが「該当なし」に化けた

DB に対して「禁止した形の外部キーが存在しないこと」を確かめる SQL を書いた。
その SQL は存在しないカラムを参照していて、実行するとエラーになる。
ところが呼び出し側が stderr を捨てていたので、目に入ったのは空の結果だけ。
「該当なし。制約は守られている」と読んだ。実際には**何も検査されていない**。

- なぜ成功に見えたか: 「結果が空」と「実行が失敗」が同じ見た目だった
- 対策: 終了コードを見る。成功時の出力にも「何を見たか」を含める

## 事例2: 検出すべきものが、検査を置いた場所には定義上存在できなかった

サービスごとに database を分けた構成で、「database を跨ぐ外部キーが無いこと」を
CI で検査することにした。検査は各サービス単位の CI ジョブに置いた。

ここに構造の穴がある。サービス単位のジョブは**自分のサービスの分しか**
マイグレーションを適用しない。相手側の database にはテーブルが無い。
跨ぐ外部キーは参照先のテーブルが無いと作れないので、このジョブの中では
**検出対象が定義上存在できない**。検査は未来永劫、成功し続ける。

- なぜ成功に見えたか: 検査のロジックは正しく、実行も成功していた。
  間違っていたのは**置き場所**で、それはコードのどこにも書かれていない
- 対策: 検査に前提の検証を持たせる。「全 database にテーブルが存在すること」を
  先に確かめ、崩れていたら検査自体を失敗させる。成功時の出力は
  「跨ぐ外部キーは無い（見た database: a, b）」の形にする

## 事例3: 生存確認は「誰が」生きているかを言わない

CI で、認証なしで動くプロセスを止め、認証ありで再起動する手順があった。
再起動の完了は `/healthz` が 200 を返すことで確認していた。

実際には旧プロセスが終了しておらず、ポートを握ったままだった。新プロセスは
bind に失敗して即死。`/healthz` のポーリングは**生き残った旧プロセス**に当たって
200 を返し、手順は「再起動成功」で通過した。以降の検査はすべて認証なしの
旧プロセスを相手に走った。

- なぜ成功に見えたか: `/healthz` は「そのポートで誰かが応答する」ことしか
  言わない。新旧どちらのプロセスかを区別する情報がない
- 対策: readiness には「**期待する実体だけが返せる応答**」を使う。この例では
  認証ミドルウェアの有無で応答コードが変わるリクエスト（認証ありなら 401、
  なしなら 400）を投げ、401 だけを起動完了とみなすようにした。ちなみに
  この修正を入れた瞬間、隠れていた真因（旧プロセスが kill に掛からない）が
  初めてエラーとして出てきた。fail open を closed に直すと、溜まっていた
  問題が音を立てて出てくる

## 事例4: 検証リクエストが対象に届いていなかった

コンテナ内の名前解決を DNS のエイリアスで曲げる構成を作り、疎通確認を
コンテナ内から curl で行った。返ってきたのは期待と違う 401。

原因は curl 自身だった。**curl 8.x は `*.localhost` の名前を DNS を引かずに
ループバックへ解決する**（RFC 6761 をツール側で実装している）。DNS の
エイリアスは正しく設定されていたが、curl はそれを見ない。検証リクエストは
エイリアスの先ではなく**自分自身**に届いていた。

- なぜ誤診しかけたか: `getent hosts` は正しい IP を返す。curl だけが違う経路を
  通る。「名前解決を確認した」と「このツールがその名前解決を使う」は別の命題
- 対策: 検証は本番と同じ経路のクライアント（この場合はアプリ本体の言語の
  リゾルバ）で行う。ツールで代用するなら IP 直指定 + Host ヘッダにする

## 事例5: 依存の解決が、黙って別のものを掴んだ

Go のマルチモジュール構成で、リポジトリ内の隣のモジュールを import した。
ローカルのモジュールを使うには go.mod に `replace` を書く必要があるが、
それを忘れた。

パッケージが公開リポジトリに存在しなければ、ここで音を立てて失敗する（無害）。
だがこのリポジトリは公開されていてパッケージも存在した。Go は**公開されている
古い版を取得し、ビルドは成功した**。手元のコードは1行も使われていないのに。

- なぜ成功に見えたか: 依存解決の仕様として正しい動作だから。壊れているのは
  「ローカルを使うつもり」という書かれていない意図のほう
- 対策: 意図を機械にする。「リポジトリ内モジュールの require には必ず対応する
  replace がある」ことを検査する lint を CI に置いた

## 共通の型

5例とも、壊れたのは本体ではなく**確かめる仕組み**で、壊れた結果は全部
「成功」だった。逆向きに言うと、検査の信頼性は次の3つで決まる。

1. **見たものを出力する。** 「該当なし」ではなく「a と b を見て、該当なし」。
   成功の出力から、何を根拠にした成功かが読めること（事例1・2）
2. **前提が崩れたら検査自体を失敗させる。** 走査対象が0件、相手のテーブルが
   空、期待する実体が起動していない——どれも「成功」ではなく「検査不能」で
   ある。検査不能を失敗として扱う（事例2・3）
3. **破ってみせてから信用する。** 検出すべき状態を意図的に作り、検査が
   失敗することを確認して初めて、その検査の成功に意味が生まれる。
   実際、この確認作業（変異テスト）が検査自体のバグを2つ見つけた

3つに共通するのは、**検査を fail closed に寄せる**という一点だ。本体のコードは
失敗すれば気づける。検査は失敗しても成功に見えるので、設計の負担のかけ方が
本体とは逆になる——疑うべきは、ずっと成功し続けているものである。
