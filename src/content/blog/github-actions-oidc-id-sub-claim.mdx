## 今北産業

1. GitHub Actions の OIDC で AssumeRole が `Not authorized` になり、aud も sub も
   プロバイダも教科書どおりなら、**実際に飛んでいる sub クレームを CloudTrail で見る**
2. **新しめの GitHub org は sub が `repo:owner@ID/repo@ID:*` という ID 入り形式**。
   従来形式 `repo:owner/repo:*` の信頼ポリシーにはマッチしない
3. 対処は信頼ポリシーに**両形式を併記**すること。ID は `gh api` で取れる

## 症状

```
Error: Could not assume role with OIDC: Not authorized to perform sts:AssumeRoleWithWebIdentity
```

`aws-actions/configure-aws-credentials` がこれで落ちます。そして定番の確認は全部通る:

- OIDC プロバイダ `token.actions.githubusercontent.com` はある。audience も `sts.amazonaws.com`
- workflow の `permissions: id-token: write` もある
- 信頼ポリシーの sub 条件も、動いている他リポジトリの実績ある形をコピーした

```json
"Condition": {
  "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
  "StringLike":   { "token.actions.githubusercontent.com:sub": "repo:myorg/myrepo:*" }
}
```

**実績ある形のコピーなのに落ちる**、が今回の罠の性質です。

## 実際の sub を見る: CloudTrail に聞く

STS の拒否は「どのクレームで来たか」をエラーメッセージに出してくれません。
拒否した側の記録 — CloudTrail — に実物が残っています:

```bash
aws cloudtrail lookup-events --region ap-northeast-1 \
  --lookup-attributes AttributeKey=EventName,AttributeValue=AssumeRoleWithWebIdentity \
  --max-results 5
```

数分待って出てきたイベントの中身がこれでした:

```
error: AccessDenied Not authorized to perform sts:AssumeRoleWithWebIdentity
sub:   repo:rikukadev@328009292/kagerou-ssr-demo@1366497913:pull_request
```

`repo:rikukadev/kagerou-ssr-demo:pull_request` を待っていた信頼ポリシーに、
**`@数字` 付きの sub** が飛んできていました。マッチするわけがありません。

## 原因: 新しめの org は sub に不変 ID が入る

GitHub は org / リポジトリの**名前再利用による成りすまし対策**として、
sub クレームに不変 ID を含める形式を導入しています。ポイントは:

- **新しく作った org はこの ID 入り形式**で sub が発行される
- **古いアカウント・org は従来形式のまま**

つまり「長年動いている個人リポジトリのロールとまったく同じ信頼ポリシーを、
新設 org のリポジトリ用に作ったのに動かない」という、再現条件が属人的な罠になります。
私はまさに、旧アカウント(従来形式で稼働中)の実績ポリシーをコピーして踏みました。

## 対処: 両形式を併記する

`StringLike` の値は配列にできるので、両方書いておけばどちらの形式でも通ります:

```json
"Condition": {
  "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
  "StringLike": { "token.actions.githubusercontent.com:sub": [
    "repo:myorg/myrepo:*",
    "repo:myorg@OWNER_ID/myrepo@REPO_ID:*"
  ]}
}
```

ID は API で取れます(リポジトリ 1 回の呼び出しで両方取れる):

```bash
REPO_ID=$(gh api repos/myorg/myrepo --jq .id)
OWNER_ID=$(gh api repos/myorg/myrepo --jq .owner.id)
```

ワイルドカードで `repo:myorg@*/myrepo@*:*` と書きたくなりますが、ID を素通しにすると
名前再利用対策という本来の意図が消えるので、実 ID を埋める方が筋です。

## 教訓

**認証・認可の拒否は、拒否した側のログに実物を聞く。** トークンの中身を推測して
信頼ポリシーをいじり回すより、CloudTrail の 1 イベントを見るほうが速くて確実です。
GitHub Actions 側からは(ログを盛っても)sub の実物は出てきません。
